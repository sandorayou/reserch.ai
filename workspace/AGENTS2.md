# 継続研究モード補足

このファイルは、ユーザーが「研究モードでお願い」「研究モード」「ループモードで研究」または同等の継続研究を明示した場合にだけ読む。通常の依頼に適用する工程管理、成果確認、障害復旧、報告ルールはユーザーレベル `AGENTS.md` に置く。研究モードでは同ファイルの通常開発と完了監督を先に適用し、ここでは研究反復に固有の条件だけを追加する。明示的な1回限り・単一比較の指定、ユーザー指定の上限を優先する。

## 研究開始ゲート
- 依頼された通常開発・デバッグ・データ取得・評価器実装を終え、利用可能な実入力で代表的なE2E成果と決定論的受入チェックを確認してから研究を始める。未完成作業を研究反復に数えない。
- 研究前に、指標、基準版A、データ/期間、初期状態、費用、モデル/設定、評価器、採否条件を固定する。Aのコード・入力・設定・結果のハッシュと再現手順を記録する。
- 最初の研究実験より前に、固定した基準と開始条件を検査する実行可能なreadiness gateを用意して実行する。記録が欠落・不正・古い・読めない、またはgateが失敗した場合は研究を開始せず、通常開発で修復する。文書上のチェックリストだけを実装済みgateと見なさない。
- 比較条件の固定・有効性確認・部分結果の扱いはグローバル `AGENTS.md` に従う。未完了の比較を次の仮説に進む根拠にせず、無効な結果や推定値を実験結果として記録しない。

## 長時間計算の時間最適化ゲート
- 高コスト計算の受入目標に「妥当な精度・科学的条件を満たす結果までの壁時計時間」を明記する。処理件数を減らす、許容誤差を緩める、収束条件を弱めることを速度改善と呼ばない。そうした変更は科学的仮説として事前登録し、同じ評価条件で精度と速度を比較する。
- 起動または再開前に実行状態を確認する。動作中のworkerを重複起動せず、停止を指示された実行を明示的な再開指示なしに起動し直さない。実行中の設定変更・停止も、依頼の明確な許可がない限り行わない。
- 全規模計算の前に、実データの代表的な小ケースまたは最小の実行可能単位で計測する。壁時計時間、CPU時間と使用率、ピークメモリ、ディスク読書き、反復/収束回数、初期化・積分生成・主要solver等の段階別時間を記録し、完了済みケースの実測値から所要時間を見積もる。根拠のないETAやCPU使用率だけからの進捗主張をしない。
- 同じ入力・中間量が再計算されていないかをソースと実行ログで調べる。高コスト中間データは再利用可能性を検討し、キャッシュキーに入力/幾何構造、物理条件、手法、基底、離散化、ソフトウェア版と重要オプションを含める。キー一致だけで再利用せず、生成元ハッシュと数値的一貫性を検証する。異なる幾何構造・条件の量を同一視してはならない。
- スレッド数、並列ケース数、メモリ上限、データ配置、I/Oを、小ケースの実測で比較し、全体の壁時計時間が最短になる組合せを選ぶ。低資源設定や全コア設定を慣例で選ばず、過剰並列によるメモリ圧迫・I/O競合・CPU oversubscriptionも測る。各候補は一要因だけ変え、同じ入力・初期状態・科学条件・精度判定で比較する。
- 最初の全規模計算を許可する実行可能ゲートは、(a)妥当な計算再利用/重複排除を調べた記録、(b)代表ケースの段階別性能計測、(c)資源設定を選んだ根拠、(d)精度・同一性を守る検証条件、(e)推定壁時計時間とチェックポイント方針が揃っていることを検査する。不足・古い・失敗した証拠があれば全規模実行を止め、限定パイロットか通常開発で補う。読み物上の宣言だけで通過扱いにしない。
- 比較後は各armの実時間、CPU/メモリ/I/O、完了件数、収束/精度、CLI回数、取得可能なtoken会計、コード・入力ハッシュを記録する。速度だけ上がって採択基準を満たさない案は不採択。実際に比較していない候補がある場合、「最速」「最大限最適化済み」と主張せず、比較範囲と未計測項目を示す。
- 各チェックポイントには、完了単位、段階別実測時間、現在の所要時間推定とその根拠、次に検討する時間短縮要因を記録する。固定間隔の状態確認を繰り返すのではなく、完了イベントや意味のある進捗差分で監視する。

## 仮説と比較
- 結果を確認する前に、各仮説の予測、変更する一要因、対象データ、指標、合格/棄却条件を記録する。結果を見てから登録した候補は探索的・post-hocと明記する。
- 1比較は「仮説登録 → 一要因だけ変更 → 同じ固定条件でA/B実行 → 実出力を検証 → 両armの結果とハッシュ、差、限界、採否理由を保存」まで完了して初めて有効。どちらかのarmが欠けた、失敗/timeoutした、出力や会計が不正な場合は未完了として修復し、別仮説へ進まない。
- 開発データで複数仮説や粗密探索を行う場合、候補数・探索範囲・全結果を残して選択バイアスを報告する。開発データで選んだ候補を独立確認と呼ばない。最終holdoutは候補と採否条件を固定するまで封印する。
- ワークフロー、プロンプト、段階構成などの候補は同じ依頼・初期状態・モデル・設定・決定論的評価器で比較し、安全ゲートを外さない。測定した受入結果を先に比べ、合格候補間だけで時間/CLI回数/入力・キャッシュ済み入力・出力tokenを比較する。測れない値は未計測とする。
- 研究上の並列実験は、仮説・採否条件を事前登録し、入力・状態・出力を分離して多重比較を報告できる場合に限る。独立した通常開発・レビューの並列化はグローバル `AGENTS.md` に従う。
- 有効な比較を3候補行って改善がなければ、局所調整を続けず別方式の仮説を立てる。同じ原因が2回出た場合は実行経路または責任層を変更する。次の仮説へ移る前に直前の両arm結果が有効であることを監督側が確認する。ゲート、評価器、閾値を結果に合わせて弱めない。

## 研究ループの起動と継続
- 起動前に `loop doctor`、対象ディレクトリの既存実行、Loopfileを確認する。正確なLoopfileを `loop run --dry <file>` で検証し、正しいCodex adapter/model、`permissions: edits`、`--sandbox workspace-write`、許可済みの入出力先、有限の1バッチ上限、およびapproval/sandbox bypassがないことを確認する。既存の実行を重複起動したり、許可なく停止したりしない。
- 研究モードを明示されたら `continuous-loop` スキルの監督方式を使う。バッチ上限、no-progress/retry guard、ターン終了は研究全体の完了ではなく再開可能な境界として記録する。ユーザー明示停止、明示された上限、事前登録した科学的停止条件、または全ての安全な独立経路が尽きた後の具体的なユーザー専用入力待ちでのみ停止する。
- 長時間処理はイベント通知方式を使う。`wake-run` が armed を返した時点では起動確認に過ぎないため、そのターンを終えて通知を待つ。通知後にworkerの終了、journal/batch記録、実成果物、verifierを確認する。生存中のworkerを二重起動しない。
- 各batchのcheckpointに、現在の仮説・最終完了比較・実結果・失敗理由・停止/再開理由・次の具体的な操作を保存する。Loop/監督クラッシュ時は `loop status`・イベント・processを確認し、最後に有効だったcheckpointから再開する。部分編集を保ち、run stateを削除/巻き戻しせず、同じ条件のdry-runを再確認してから起動する。
- approval/sandboxやグローバル設定を弱めない。起動失敗時はCLI、adapter、Loopfile、権限、cwdを切り分け、同じ失敗の盲目的な再試行をせず安全な別経路を使う。usageや費用が計測できない場合、制御できているとは主張しない。

## 研究結果の記録
- 各比較の両armについて、受入結果、終了/検査結果、CLI回数、実時間、入力・キャッシュ済み入力・出力token、変更パス、ソース/入力ハッシュを記録する。token数はキャッシュを入力の内数として扱う。
- 調査、データ取得、fixture、監査、テスト成功、プロセス生存は準備作業であり、ユーザー向けA/B比較の代わりや研究改善件数にしない。
- 最終報告で基準Aとの差と試行数、対象範囲、欠損、選択バイアス、測定限界を示す。限定データの結果を一般的な性能向上と主張しない。研究ループを止める場合は、ユーザー停止・明示上限・事前登録した科学的停止条件・具体的な入力待ちのどれかをcheckpointに正確に記録する。
